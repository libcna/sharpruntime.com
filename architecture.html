Architecture

A native C++ compatibility layer organized into independently selectable, boundary-validated CMake components.

41 physical components92 direct edgesNo dependency allow-list

Conceptual layers

LayerRole
Consumer codeNative application or source port using familiar System::* names
Curated compatibility APIHeaders and behavior for the practical implemented subset
Physical componentsOwnership units for headers, implementation, tests and dependencies
Native/platform layerC++ standard library, OS facilities and narrowly attached vendor dependencies

Component ownership

Each module directory owns include/, optional src/, tests and one CMake registration. A component is either a static library or an interface/header-only target. Public, private and test dependencies are distinct.

Edge kindMeaning
PublicA public header uses the dependency; include/link requirements reach consumers
PrivateOnly implementation sources use the dependency; static-link needs remain correct without leaking include roots
Test-onlyAvailable to the owning test binary, not production consumers

Boundary enforcement

The independent validator parses the registered graph and source includes. It rejects duplicate ownership, orphan production files, undeclared or stale edges, visibility mismatches and cycles. The current allow-list is empty.

Native object model

Sharp Runtime uses ordinary C++ objects, values, templates, RAII and smart pointers. There is no tracing collector. Compatibility wrappers and macros help port familiar shapes, but C++ lifetime, copy/move and aliasing rules remain in force.

External dependency isolation

ZLIB, miniz, tinyxml2, platform socket/crypto libraries and Android SDL integration attach to their narrow owners. This is what makes a Text.Json-only configuration meaningfully smaller than All.
